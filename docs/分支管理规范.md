# skill-api 分支管理规范

> 适用范围：本仓库所有 Git 分支的创建、命名与生命周期管理。
> 制定依据：GitFlow / Trunk-Based / GitHub Flow 等主流实践调研（腾讯云分支规范、Conventional Branch 约定式分支、Google/Facebook 主干开发工程实践），结合本项目「单人开发 + GitLab 主远程 + GitHub 镜像 + 按需部署」的实际情况裁剪。

## 1. 分支模型

本项目采用**简化版 GitFlow**：

- `dev`：主开发主干。所有功能分支从这里拉取、最终合入这里，是日常开发的唯一主干
- `main`：生产分支。仅接受 `release/` 分支合入或经验收的 `dev` 合并，不在其上直接开发
- `feature/*` 等临时分支：短生命周期（见 §3），用完即删

**不采用**的模型及原因：

- 完整 GitFlow：`develop → release → master` 多级流水对本项目过重，发布按需走 `release/` 分支即可
- Trunk-Based（Google/Facebook 式）：需要高 CI 成熟度与高频小合并，单人项目收益低

## 2. 命名规范

统一格式：**`<类型>/<描述>`**，描述使用**小写 kebab-case**（连字符分隔）。

| 前缀 | 用途 | 示例 |
|------|------|------|
| `feature/` | 新功能 / 新接口 | `feature/order-batch` |
| `fix/` | 普通 Bug 修复 | `fix/logs-truncate` |
| `hotfix/` | 线上紧急修复（从 `main` 拉取，修复后回合 `main` 与 `dev`） | `hotfix/price-id-500` |
| `release/` | 发版收敛（从 `dev` 拉取，验收后合 `main` 并打 tag） | `release/v1.2.0` |
| `refactor/` | 代码重构（行为不变） | `refactor/fee-mapping` |
| `docs/` | 纯文档改动 | `docs/branch-guide` |
| `test/` | 纯测试补充 | `test/bill-import` |

禁止项：人名、日期、泛化词（`work` / `dev` / `temp`）、大写驼峰、下划线风格。

## 3. 生命周期

1. **来源**：一律从 `dev` 拉取（`hotfix/` 除外，从 `main` 拉取）
2. **分支要短命**：单个功能分支尽量在数日内完成并合入，避免长期分叉（教训：`feature/bill-import` 曾积压 24 个提交才合入，增大了合并冲突面）
3. **合入即删**：合入 `dev` 后删除远程分支（`git push origin :<分支名>`），本地分支按需清理，GitLab 上不堆积
4. **发版**：`dev` 验收后拉 `release/x.y.z` → 测试收敛 → 合 `main` 并打 tag → 删除 `release/` 分支
5. **冲突解决**：两分支改同一文件时，保留实现更完整的一方，删除重复/基础版本

## 4. 与提交规范对齐

分支前缀与 Conventional Commits 提交前缀保持一致：

| 分支前缀 | 提交前缀 |
|----------|----------|
| `feature/` | `feat:` |
| `fix/` / `hotfix/` | `fix:` |
| `docs/` | `docs:` |
| `refactor/` | `refactor:` |
| `test/` | `test:` |

保证「提交前缀 = 分支前缀」，CI 与 changelog 工具链识别统一，如 `feat(logs): …` 对应分支 `feature/logs-*`。
