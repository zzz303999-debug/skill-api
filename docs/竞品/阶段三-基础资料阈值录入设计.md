# 阶段三（种子）：基础资料阈值录入设计

> 来源：用户 2026-08-14 决策——「竞品识别：订单数据和财务数据完成，基础资料要筛选，客户和工厂地址超过 N 次才录入，司机和车辆超过 N 次才录入（建议 5 次）」。
> 状态：**已实施完成（2026-08-14，见《实施prompt-阶段三-基础资料阈值建档》T17-T23）**。口径锁定见 §4；建档接口逆推全部就绪见 §5。

## 1. 决策原文转述

竞品账单导入 TMS 时，订单数据与财务（费用）数据照常录入；**基础资料（档案）不无条件自动建档**，而是按出现次数筛选：

| 档案类 | 规则 |
|---|---|
| 客户 | 累计出现 > N 次才录入 TMS 客户档案 |
| 工厂地址 | 累计出现 > N 次才录入工厂/地址档案 |
| 司机 | 累计出现 > N 次才录入司机档案 |
| 车辆 | 累计出现 > N 次才录入车辆档案 |

**N 默认 5，必须做成配置项**（`master_data.threshold: 5`），不进代码。

## 2. 设计要点（初稿）

1. **计数存储**：需要新增一个轻量计数器（按档案类 + 归一名累计出现次数），跨导入批次持久化——这是本阶段唯一的新基础设施。归一规则沿用阶段一 normalizers（去空格/全半角/大小写），防止「锦煦 」「锦煦」算两个；
2. **与既有客户修复联动**：修复 prompt 的 F3 `customer_resolve` 策略升级——命中档案 → 用 `c_id`/`c_title`（EX26080031 实证客户档案字段）；未命中 → 计数 +1，**达阈值才调建档接口**；未达阈值 → 订单照常提交（文本名），仅在对账报告标注「未建档（计数 x/N）」；
3. **阈值判定时机**：在聚合后、payload 构造前——同一批导入内多次出现的档案要能跨单累计（一批文件里出现 5 次也应触发建档）；
4. **司机+车辆**：TMS 侧司机/车辆是派车段 `driver[0]` 的 `d_name`/`d_num`/`d_phone` 关联档案（响应回显 `driver_id`/`car_id`），建档接口待抓包逆推（同价格表建档套路）。

## 3. 与既有文档的关系

- 客户档案字段证据（`c_id`=166328 / `c_title`）见逆推规范 §2.2 与《修复prompt-客户名称误入联系人字段》F2；
- 价格表建档接口（逆推规范 §8）证明了「建档类接口」的存在与形态，客户/司机/车辆建档接口同法逆推；
- 阶段二 prompt 不受影响（费用通道不碰档案建档）。

## 4. 口径最终决策（2026-08-14 用户拍板）

| # | 问题 | **决策** |
|---|---|---|
| 1 | 计数键：客户按名称精确匹配？工厂按「地址全文」还是「工厂名+地址」？ | ✅ 客户按归一名；工厂按「名+地址」复合键（默认采纳） |
| 2 | 司机与车辆：分别计数还是「司机+车牌」组合计数？ | ✅ **「司机+车牌」组合计数**——同人换车/同车换人算不同档案 |
| 3 | 计数范围：跨全部模板家族累计，还是按家族分开？ | ✅ **跨全部模板家族全局累计** |
| 4 | 未达阈值时订单里的档案字段：照常带文本，还是留空？ | ✅ **照常带文本提交 + 对账报告标注「未建档(x/N)」**，订单不阻塞 |
| 5 | 阈值触发后：当批建档还是下批生效？ | ✅ **当批建档、当批回填**（默认采纳） |

## 5. 建档接口逆推进度（2026-08-14 **全部就绪**）

| 档案类 | 建档接口 | 关键回值 | 状态 |
|---|---|---|---|
| 价格表费目 | 逆推规范 §8 | `price_id` | ✅ 已逆推 |
| 客户 | 逆推规范 §9（client_name + 分组 cg_id + 联系人 data[0][n/p] 数组） | `client_id` → 订单 `c_id`/`cg_id` 回填 | ✅ 已逆推 |
| 委托人（发货方） | 逆推规范 §10（bailor_title + 联系人 + address 单值） | `bailor_id` | ✅ 已逆推 |
| 司机 | 逆推规范 §11（**带车牌 num + 关联 truck_id**，日期区间双写；num/phone 必填） | `id`（✅ 2026-08-14 实证启用：AddCarDriver 端点，响应带 data.id） | ✅ 已逆推 + 已启用 |
| 车辆 | 逆推规范 §12（num=车牌，section_id=部门，保险/证件全集可空） | `truck_id` | ✅ 已逆推 |
| 工厂地址 | 逆推规范 §13（**前置 client_id**，四级区划，adcode 可推导） | `factory_id` → 订单 factory_id 回填 | ✅ 已逆推 |

**依赖图（建档顺序）**：客户 → 工厂地址；车辆 → 司机；委托人 → 司机（可选）；价格费目独立。
**端点 URL 六个全部待补**（抓包未带请求行）→ 已做成 `config/master_data.{env}.yaml`（APP_ENV 选择，test/prod 双份随镜像分发）的 endpoints 配置项，占位 TODO 待填；未填前对应档案类自动降级为只计数不建档（不 fail fast）。

**已逆推接口的共同要点**：① 均为 form-data + `code:200` 判定，与订单/价格表同构，client.py 可直接复用通道；② 抓包均带测试脏数据（价格 124823 / 客户 169642 / 委托人 159132），建议测试环境清理；③ 客户建档会**随建价格记录**（price_item=出车费 rate=10），程序建档时必须裁剪 price_* 字段，只发最小字段集；④ 委托人响应 `add_time` 是 unix 串、客户是格式化串——响应解析按字段存在性取值，不假设格式。

**最小建档字段集（程序建档用，防污染档案）**：
- 客户：`client_name` / `sn` / `cg_id`(+`cg_name`) / `su_id` / `data[0][n]`+`data[0][p]`（联系人数组）；
- 委托人：`bailor_title` / `sn` / `name` / `tel` / `address`；
- 费目：`name` / `sn` / `class_id`(+`classification_name`) / `is_get`/`is_pay` / 默认值组。
