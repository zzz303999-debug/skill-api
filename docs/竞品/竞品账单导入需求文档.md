## 2. 背景与目标

### 2.1 背景

系统中沉淀了大量历史应收对账单（`.xls` / `.xlsx`，如「2018-01到2018-12上海秋怡应收对账单.xls」）。切换至本 TMS 系统后，这批历史业务数据需要导入，否则：

- 历史订单无法在 TMS 中查询、追溯、续做业务
- 账单中的客户、提单号、柜型柜量、做箱日期等业务信息需要人工逐行录入，成本高且易错

竞品账单单文件可达数千行（实测样例 6450 行、归集约 3980 单），且存在**一票多柜**（同一提单号多行记录）、**日期缺年份**（账单内只有月-日）、**表头列序不固定**等数据特征，无法直接平移导入。

### 2.2 目标

- 将竞品导出的应收对账单**自动解析**为 TMS 业务订单数据，按提单号归集（一票多柜合并为一单），映射为业务订单新增接口（`AddWork`）所需字段
- 提供**预览 → 人工确认 → 逐单创建**的完整导入闭环，保证数据安全
- 关键字段（提单号、客户）**宁可人工复核，不可静默出错**

### 2.3 范围界定

- 本文档仅描述**业务信息**数据线的导入：竞品账单 → 解析归集 → 创建业务订单
- 不在本期范围：财务信息（应收/应付费用）、基础信息、费用栏目等数据线；账单数据不落库，以导入结果为准

### 2.4 核心设计原则

1. **默认不自动下单**：开关缺省为"只预览"；调用方显式传 `true` 才直接创建，防止误下单
2. **一票一单**：同提单号的多个柜子合并为一个业务订单
3. **零静默错误**：提单号、客户等关键字段缺失时**不阻塞接口返回**，但必须标记人工确认；关键数字宁缺勿错（缺失字段不填 0、不填空串）
4. **不自动重试**：订单创建请求不自动重试，防止重复下单；失败单由调用方处理后重新提交
5. **原文保真**：提单号、箱号、客户名等逐字复制，不做"智能改写"

## 3. 名词解释

| 术语 | 说明 |
|---|---|
| 竞品系统 | 金科信等第三方货代业务，导出历史应收对账单 |
| 应收对账单 | 竞品系统按结算周期导出的账单文件，一文件一个结算周期（如 2018-01 至 2018-12），每柜一行 |
| 结算区间 | 账单抬头标注的结算日期范围（如 `2018-01-01-2018-12-31`），用于日期补年份 |
| 提单号 | 订单号（order_num1）。≥8 位，仅数字或字母数字；**纯字母（船名）不算** |
| 一票多柜 | 同一提单号对应多个柜子，账单中表现为多行记录 |
| 归集 | 按提单号将多行账单记录合并为一个业务订单的过程 |
| 业务编号 | 竞品账单中带柜序号后缀的内部编号（如 `17120321-1`），对应 `c_sn` |
| AddWork | 下游 TMS 系统的业务订单新增接口 |
| 人工确认 | 系统无法高置信确认字段值时，由人工审核确认的流程（needs_confirmation 机制） |
| 预览模式 | 只解析不下单，返回归集结果与缺失清单供人工核对 |
| 创建模式 | 解析后直接逐单调用下游创建订单，同时返回解析结果与每单创建结果 |

## 4. 产品定位与使用场景

### 4.1 定位

面向"竞品数据迁移"的**批量账单导入能力**：一次上传一份竞品账单，服务端完成解析、归集、映射，输出可直接人工核对或直接创建订单的结构化结果，作为业务订单新增接口的上游数据线。

### 4.2 典型使用场景

1. **历史账单批量迁移**：切换 TMS 系统时，将竞品导出的一批历史对账单逐份导入，快速重建历史业务订单
2. **导入前预览核对**：先以预览模式导入，人工核对归集结果与缺失字段，确认无误后再正式创建
3. **直连创建**：对数据质量有信心的账单，直接以创建模式导入，一次性逐单创建订单
4. **失败单补救**：创建模式下个别订单失败（下游拒绝/超时），调用方根据逐单错误结果修正后重新提交

## 5. 功能需求

### 5.1 账单文件解析

**输入**：单份竞品应收对账单文件（`multipart/form-data` 上传）

**支持格式**：`.xls` / `.xlsx` / `.xlsm`；大小上限 20 MB

**文件真实性校验**：按文件内容（而非扩展名）识别真实格式；扩展名与内容不符、空文件、损坏/加密文件均拒绝并给出中文错误说明。

**账单识别依据**：表头需**同时含「业务编号」「提单号」两列**才识别为有效账单，否则返回错误；表头按**列名**匹配（而非固定列号），账单列顺序变化不影响解析。

**输出**：`orders[]` 归集后的订单列表（每单含 order_data、缺失字段、人工确认标记）+ 结算区间 + 溯源元信息（文件哈希、解析时间、解析引擎）。

### 5.2 一票多柜归集规则

按提单号分组，同一提单号的所有行合并为一个业务订单：

| 维度 | 规则 |
|---|---|
| 分组 | 按提单号分组；提单号为空的行**单独成组**并标记人工确认（避免与其他票错误合并） |
| `box[]` | 同箱型数量累加（如 2 行各 40HQ → `[{"b_type": "40HQ", "box_num": 2}]`）；箱型必须为 4 位标准格式（20/25/40 + 两位字母），非法箱型跳过 |
| `data[]` | 每柜一行，仅含该行提单号；组内行按账单「序号」排序，保证顺序与账单一致 |
| `driver[]` | 合并后仅一条，`b_date` 取组内第一条（按序号排序）的日期；各柜日期不一致时，其余日期并入备注 `c_note` |
| 箱号 | AddWork 无箱号字段，全部箱号汇总写入备注 `c_note` 兜底，不丢数据（如「箱号：OOLU7929509,...」） |
| 业务编号 | 含柜序号后缀（如 `17120321-1`）时，归集时去掉 `-N` 后缀取票号写入 `c_sn` |

### 5.3 日期补年份规则

账单内日期通常只有月-日（如 `1-27`），年份从账单抬头「结算区间」推断：

- 优先取**落在结算区间内**的年份（跨年账单如 `2018-01~2019-12` 时，`12-7` 补为 `2018-12-07`、`1-5` 补为 `2019-01-05`）
- 无法推断（日期非法、无结算区间）→ `b_date` 置 null 并标记人工确认
- 月份 `month`（`YYYY-MM`）从补年份后的账单日期推导；`b_date` 缺失时 `month` 同样置空

### 5.4 字段映射与缺失处理

账单列 → 订单字段映射（业务信息线）：

| 账单列 | 订单字段 | 必填 | 说明 |
|---|---|---|---|
| 提单号 | `order_num1` | ✅ | 订单号=提单号；≥8 位，仅数字或字母数字；清洗空格/连字符；纯字母不算 |
| 客户名称 | `c_title` | ✅ | 托运人/公司名称 |
| 业务编号 | `c_sn` | ❌ | 归集时去掉 `-N` 后缀 |
| 客户编号 | `c_note` | ❌ | 请求无对应字段，暂入备注 |
| 业务类型（进口/出口） | `c_note` | ❌ | 请求无进出口字段，`type` 固定 1，暂入备注 |
| 门点 / 装卸点 | `factory_name` / `factory_bei` | ❌ | |
| 提箱点 / 还箱点 | `driver[0][b_get_address]` / `driver[0][b_back_address]` | ❌ | |
| 船名/航次 | `b_ship_name` / `b_ship_num` | ❌ | 按 `/` 拆分：前段=船名、后段=航次；无分隔符时整段归船名 |
| 船公司 | `b_ship_company` | ❌ | |
| 做箱日期 | `driver[0][b_date]` | ❌ | 按 5.3 规则补年份，格式 `YYYY-MM-DD`；无法推断 → null + 人工确认 |
| 箱型 / 箱量 | `box[N][b_type]` / `box[N][box_num]` | ❌ | 同型累加；非法箱型跳过 |
| 箱号 | `c_note`（兜底） | ❌ | AddWork 无箱号字段，全部汇总入备注 |
| 备注 | `c_note` | ❌ | 追加到备注尾部 |
| 月份 | `month` | ❌ | `YYYY-MM`，从补年份后的日期推导 |

**缺失处理（软校验）**：

- 字段缺失**不报错**（返回 200 + 人工确认标记），只有文件级/请求级问题才返回非 200
- 每个缺失字段标注中文原因：`原文未找到，请人工确认` / `格式不合法`
- 缺失字段在 order_data 中保持 **null**（不会用空字符串或 0 填充），发送 AddWork 时展平为空字符串

### 5.5 人工确认机制

`needs_confirmation=true` 的触发条件（满足其一）：

| missing_fields | 触发条件 | 原因取值 |
|---|---|---|
| `order_num1` | 提单号为空，或清洗后不足 8 位/含非法字符/纯字母 | `原文未找到，请人工确认` / `格式不合法` |
| `c_title` | 客户名称为空 | `原文未找到，请人工确认` |
| `b_date` | 日期为空或补年份失败 | `原文未找到，请人工确认` / `格式不合法` |

- `needs_confirmation=false` 表示业务信息必填字段齐备，可安全提交
- **人工确认标记不下发下游**：创建模式下 `needs_confirmation=true` 的订单照常提交（开关语义是"是否创建"，不是"是否放行"），是否拦截由调用方自行判断
- 预览模式下修正缺失字段的方式：**修改文件后重新导入**（单接口模式无独立提交通道）

### 5.6 订单创建（创建模式）

创建模式下，服务端按以下链路逐单创建订单（v1.4 起，2026-08-19）：

```
① 调用方登录 TMS（页面/系统登录）→ 获得 token（sk 值）
② POST /orders/bill/import（multipart，create_order=true，请求头 sk: <token>）
③ AddWork × N（逐单创建业务订单，携带同一 sk 令牌；建档/费目自举同用）
```

- **sk 由调用方透传，逐单创建**：调用方登录 TMS 获取 token 后经请求头 `sk` 透传（一次），再串行调用 ③；某单失败不影响后续订单
- **sk 无效/过期由下游判定**：AddWork 端拒绝 → 该单 error 透传（不抛整请求错误）；调用方需重新登录 TMS 获取新 token
- **create 模式缺 sk 头** → 400 `bad_request`（不进入解析/下单流程）；preview 模式零下游调用不要求
- **服务端不再持有任何 TMS 凭据**（原 GetWebKey → login 链路及 JXT_EXT_* 配置已移除）；调用方传入的 sk 仅作下游鉴权透传，不写入响应
- **创建结果逐单透传**：每单返回 `{success, sn, error}`；成功时 `sn` 为下游订单编号，失败时完整透传下游错误（含 code/msg/响应原文）
- **不自动重试**：下游超时/拒绝时不重试（防重复下单）；调用方在结果不明确时不应盲目重试（下游可能已创建但响应超时）

### 5.7 审计与溯源

- 请求/响应自动写入访问日志（含文件哈希、订单数、逐单创建结果），可在 `/logs` 页面查询
- 响应携带 `meta`：文件 SHA-256、字节数、解析时间、解析引擎，保证结果可溯源

## 6. 非功能需求

### 6.1 性能与容量

| 项 | 值 | 说明 |
|---|---|---|
| 单文件大小上限 | 20 MB | 超限返回错误，不截断处理 |
| 单次导入订单数建议 | ≤ 2000 单 | 超出建议拆分文件导入 |
| 创建模式耗时 | 分钟级 | 订单逐单串行创建，大账单耗时较长；建议调用方放宽客户端超时 |
| 解析并发 | 4（可配） | 服务端线程池执行；满负荷排队超 10 秒返回 503 |

### 6.2 限流

- 接口属 **heavy 档**（与 `/orders` 同档）：默认 60 秒内每 IP 10 次
- 生产环境建议开启限流；内网 IP 可配白名单豁免
- 被限流请求仍写入访问日志，审计留痕完整

### 6.3 安全

- **接口鉴权**：Bearer Token 或 X-API-Key（生产必须开启）
- **下游凭据（v1.4）**：服务端不持有任何 TMS 凭据；调用方登录 TMS 获取 token 后经请求头 `sk` 透传（create 模式必填），不写入响应、不记日志明文
- **最小透传**：`userId`/`roomId` 仅作调用上下文与审计回传，不下发下游
- **错误不泄露内部实现**：下游原始响应仅在 details 中按需透传，description 为可展示给用户的中文说明

### 6.4 可用性

- 复用 skill-api 既有部署体系（容器化 + 健康检查 + 自动重启 + 部署脚本回滚）
- 单笔订单创建失败不阻塞整批导入（失败隔离）

## 7. 接口契约（概要）

完整接口级契约见 [竞品账单导入接口文档](./竞品账单导入接口文档.md)（v0.2）。

**接口形态（单接口 + 开关）**：

| 项目 | 值 |
|---|---|
| 路径 | `POST /orders/bill/import` |
| 内容类型 | `multipart/form-data` |
| 鉴权 | 需要（Bearer Token 或 X-API-Key） |
| 限流档位 | heavy（默认 60 秒内 10 次） |

**请求参数**：

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `file` | file | ✅ | 竞品应收对账单，`.xls` / `.xlsx` / `.xlsm`，≤ 20 MB |
| `create_order` | bool | ❌ | `false`（缺省）只预览不下单；`true` 逐单创建 |
| `userId` / `roomId` | string | 条件必填 | 仅作调用上下文与审计回传，不下发下游；`create_order=true` 时必须提供 |

**响应**：统一含解析结果（file / bill_period / total_rows / order_count / orders[] / meta）；仅创建模式附带 `orders[].create_result` 与 `summary`（total / success / failed）。

**主要错误码**：400 `bad_request` / `file_format_mismatch` / `file_too_large` / `empty_file`、413 `payload_too_large`、422 `convert_error`、502 `order_upstream_error`、429 `rate_limited`、503 `server_busy`、500 `internal_error`。账单内字段缺失不报错（200 + 人工确认标记）；单笔创建失败不触发整请求错误。

## 9. 质量保障

- **真实账单回归**：使用真实竞品账单样例（如「2018-01到2018-12上海秋怡应收对账单」）验证解析、归集、映射正确性；期望输出含归集后订单数与关键字段值
- **单元测试覆盖**：日期补年份（含跨年区间）、一票多柜归集（箱型累加、driver 合并、空提单号分组）、提单号校验、字段映射与缺失标记、错误处理
- **关键场景用例**：缺年份日期、一票多柜、非法箱型、空提单号、跨年结算区间、文件格式不符

## 10. 已知限制与后续规划

### 10.1 当前限制

- 仅支持"修改文件后重新导入"的人工修正方式，无独立提交通道
- 创建模式逐单串行，大账单耗时较长
- 费用线（应收/应付/成本）不在本期范围，账单中的财务数据不导入
- 箱号无下游接口字段，汇总入备注可能超长（待与下游确认接受度）
- 业务类型（进口/出口）、客户编号无下游接口字段，暂存备注
- 下游凭证不缓存，每次导入均需重新获取

### 10.2 后续规划

- 凭证缓存（按实测有效期优化，降低鉴权开销）
- 费用栏目导入（财务信息数据线）
- JSON 直传模式（不依赖文件，调用方直接传归集后数据）
- 异步任务队列（超大账单后台处理 + 结果查询）
- 与现有 `publishCreateOrder`（client.py 已对接）关系的确认：替换 / 并存
