# 竞品对账单解析 → TMS 业务订单接入设计

> 范围：四类归集中的第一类「业务信息 → 业务中心 → 业务订单 → 业务订单新增接口」。
> 核心原则：**模板配置驱动，不为单个竞品写硬编码**——后续新模板只加配置，不改代码。

---

## 1. 文件摸底结论（37 个样本）

### 1.1 模板家族

按「纯表头签名」聚类，37 个文件 = **19 个表头签名 ≈ 8 个模板家族**：

| 家族 | 文件数 | 列数 | 表头签名数 | 结构特征 |
|---|---|---|---|---|
| 军羽·应收对账单 | 11 | 16 | **1**（最稳定） | 单行表头 r5，费用列少（运费/打改单/其它/税金/小计） |
| 通寰·应收对账单 | 5 | 32 | **1**（稳定） | 单行表头 r5，费用列中等 |
| 秋怡·应收对账单 | 6 | 32~38 | 6（逐年漂移） | 单行表头 r5，费用列多且逐年增删 |
| 志驿·利润明细表 | 8（4 年 × 2 重复） | 58~62 | 4（逐年漂移） | **双行表头**（r5 区块：应收/应付/车辆成本/公司成本） |
| profitStatement·利润明细表 | 2 | 94/96 | 2 | 双行表头，与 1111 版词汇几乎不相交（不同 TMS 导出） |
| 亚灏·利润明细表 | 1 | 164 | 1 | 双行表头，费用列 100+，存在合并单元格导致的空表头 |
| 赢辉·利润明细表 | 1 | 117 | 1 | 单行表头 r5 |
| 应付账单（xlsx） | 2 | 18/37 | 2 | 表头在 r1，含 Excel 公式、合计行、制单人页脚 |

### 1.2 对架构有决定性影响的 5 个事实

1. **同家族内表头逐年漂移**：秋怡 2018 比 2016 多「搞定箱子/搬移费/税金」，2019 再多「理货费/过磅费」，2021 又删掉 6 列；志驿同理。→ 指纹精确匹配必然失效，需要「族级近似匹配 + 可选列」。
2. **双行表头 + 同名冲突**：利润明细表家族中「运费/待时费/其它费」在应收、应付两个区块下重名。→ 列映射必须**区块感知**（`区块.列名` 才是唯一键），仅靠列名会张冠李戴。
3. **表头词汇跨竞品不相交**：同一语义有大量别名——日期/到厂时间/做柜日期(年-月-日)，客户名称/客户简称，箱型/箱型箱量，提箱点/提箱堆场/提箱场站，装卸点/装卸货地点/装货地点。→ 需要**字段别名字典**，映射到标准字段。
4. **脏数据模式多样**：日期是 `1-1` 字符串（年份要从文件名/结算日期行推）；也有完整日期 `2021-01-01` 和 datetime；车牌号/提单号被 Excel 存成数字（`6588.0`、`574848870.0`）；封条号混文本（`1/14号收`）；xlsx 里有 `=Round(SUM(...))` 公式。→ 归一化是独立管线，与模板解耦。
5. **非数据行**：合计行、制单人页脚、空行。→ 行过滤规则（序号列为数值 = 数据行）也是配置项。

## 2. 总体架构

```
┌─────────────────────────────────────────────────────────────┐
│  上传 (.xls/.xlsx)                                           │
└──────────────┬──────────────────────────────────────────────┘
               ▼
┌──────────────────────────┐
│ ① 引擎适配层              │  xlrd / openpyxl → 统一 SheetView
│   （与 bill-import 已有    │  （行/列/合并单元格访问接口一致，
│    _SheetView 同思路）     │   上层不感知文件格式）
└──────────────┬───────────┘
               ▼
┌──────────────────────────┐
│ ② 模板识别（三级漏斗）     │
│   L1 精确指纹命中 ────────→│  表头签名 hash 精确匹配 → 直接用配置
│   L2 族级近似匹配 ────────→│  列名集合相似度 ≥ 阈值 → 用族配置 +
│                            │  缺失列记 missing（不报错）
│   L3 AI 映射（新家族） ───→│  LLM 对表头区做字段映射 → 四道校验
│                            │  → 人工确认 → 固化为新配置
└──────────────┬───────────┘
               ▼
┌──────────────────────────┐
│ ③ 配置驱动列映射           │  YAML/JSON 模板配置：
│   （零代码接入新模板）      │  表头定位 + 区块结构 + 列映射 +
│                            │  行过滤 + 归一化规则引用
└──────────────┬───────────┘
               ▼
┌──────────────────────────┐
│ ④ 归一化管线              │  日期补年份 / 数字尾巴清洗 /
│   （模板无关，全局共享）     │  金额解析 / 箱型解析 / 一票多箱展开
└──────────────┬───────────┘
               ▼
┌──────────────────────────┐
│ ⑤ 标准业务订单模型         │  CanonicalOrder（TMS 字段的子集超集，
│                            │  四类归集共用：业务/费用/箱/…）
└──────────────┬───────────┘
               ▼
┌──────────────────────────┐
│ ⑥ TMS 接口适配层           │  CanonicalOrder → 业务订单新增接口
│                            │  payload；预览模式 / 直连模式；
│                            │  单失败隔离、凭证失败 502、不自动重试
└──────────────────────────┘
```

**关键点：竞品差异只存在于 ②③ 两层（识别 + 配置）；④⑤⑥ 对所有模板完全通用。** 接入第 9 个模板家族时，唯一动作是新增一份 YAML 配置（或走 L3 自动生成 + 人工确认）。

## 3. 模板配置 Schema（核心设计）

```yaml
# templates/junyu_v1.yaml —— 军羽应收对账单（16列，单行表头）
template_id: junyu_v1
family: junyu
name: 上海军羽·应收对账单
match:
  fingerprint: "2652ad46"        # L1 精确指纹（表头归一化 hash）
  family_min_overlap: 0.85       # L2 族级近似：列名集合重合度阈值
header:
  row_anchor: "序号"              # 表头行定位锚点（不硬写行号）
  two_row: false                  # 单行表头
data:
  row_filter: "seq_numeric"       # 序号列为数值 → 数据行；其余（合计/页脚/空行）跳过
  stop_on: ["合计"]               # 可选：遇到即终止
columns:                          # 列映射：标准字段 ← 源列（支持别名列表）
  order_date:    ["日期", "做箱时间"]     # 军羽无日期列时回落到做箱时间
  customer_name: ["客户名称"]
  customer_no:   ["客户编号"]
  bl_no:         ["提单号"]
  box_type_qty:  ["箱型箱量"]
  container_no:  ["箱号"]
  port_area:     ["港区"]
  driver_name:   ["司机"]
  remark:        ["应收备注"]
normalizers:                      # 归一化规则引用（全局共享实现）
  order_date: month_day_with_year # '1-1' + 文件名年份 → 2018-01-01
  bl_no: strip_float_tail         # 574848870.0 → '574848870'
  box_type_qty: box_parse         # '40HQ*2' → [{type:40HQ, qty:2}]
year_source: filename             # 年份来源：文件名 '2018-01到2018-12' 或表头上方结算日期行
```

```yaml
# templates/zhiyi_v2017.yaml —— 志驿利润明细表（双行表头，区块感知）
template_id: zhiyi_v2017
family: zhiyi
header:
  row_anchor: "序号"
  two_row: true                   # 双行表头：上一行为区块名（应收/应付/车辆成本/公司成本）
  section_fill: forward           # 区块名合并单元格 → 向右填充
columns:
  # 业务字段：无区块前缀
  order_date:    ["日期"]
  biz_no:        ["业务编号"]
  bl_no:         ["提单号"]
  container_no:  ["箱号"]
  seal_no:       ["封条号"]
  vessel:        ["船名"]
  voyage:        ["航次"]
  box_type_qty:  ["箱型箱量"]
  # 费用字段：必须带区块前缀，解决同名冲突（应收.运费 ≠ 应付.运费）
  recv_fees:
    运费:   ["应收.运费"]
    待时费: ["应收.待时费"]
    预提费: ["应收.预提费"]
    合计:   ["应收.合计"]
  pay_fees:
    运费:   ["应付.运费"]
    合计:   ["应付.合计"]
optional_columns: ["预进港", "落/还箱费", "提箱费"]   # 族内漂移列：缺失不报错，记 missing
```

**一份配置 = 表头定位 + 区块结构 + 列映射 + 行过滤 + 归一化引用 + 年份来源**，六项全是声明式，无任何 Python 代码。

## 4. 字段别名字典（全局，跨模板共享）

新模板走 L3 AI 映射时，先查字典再问 LLM，命中率越高越省 token、越稳定：

```yaml
# alias_dictionary.yaml（ starter，随模板接入持续累积 ）
bl_no:         [提单号, 副提单号]

customer_name: [客户名称, 客户简称, 结算单位]
box_type:      [箱型, 箱型箱量]
pickup_point:  [提箱点, 提箱堆场, 提箱场站]
return_point:  [还箱点, 还箱堆场, 落箱点]
load_address:  [装卸点, 装卸货地点, 装卸货地址, 装货地点, 卸货地址]

vessel:        [船名]
voyage:        [航次]
```

## 5. 归一化管线（模板无关，全部可独立测试）

| 规则 | 处理的脏数据 | 样本来源 |
|---|---|---|
| `month_day_with_year` | `1-1` → `2018-01-01`（年份来自文件名/结算日期行，跨年 12→1 月自动进位） | 通寰/军羽/秋怡/志驿 |
| `strip_float_tail` | `574848870.0` → `574848870`，`6588.0` → `6588` | 各家族车牌/提单号/封条号 |
| `box_parse` | `40HQ`、`40HQ*2`、非标箱型（大冷/飞翼） | 全部 |
| `fee_number` | 数字/中文大写/空 → Decimal；非数字原文保留进 remark | 费用列 |
| `formula_value` | xlsx 公式取计算值，不取公式文本 | 应付账单 |
| `vessel_voyage_split` | `MAERSK SARNIA/752E` 拆分 | 秋怡 |

## 6. 数据行识别与一票多箱

- **数据行**：序号列 = 数值（`1.0`、`2.0`…）。合计行（`合计:`）、制单人页脚、空行自然被滤掉。
- **一票多箱**：同提单号/同业务编号连续多行（秋怡 6 行同 `OOLU4044379500` 各带一个箱号）→ 归集规则是配置项：`group_by: [bl_no]` 或 `[biz_no]`，箱号/箱型聚合成列表。最终是「一单一箱」还是「一单多箱」调用业务订单新增接口，取决于 TMS 接口定义（**待确认，见 §8**）。

## 7. 与既有 bill-import 模块的关系

本设计与 `feature/bill-import` 已有架构（_SheetView 引擎适配 / 模板指纹库 / AI 表头映射四道闸门 / 归集器 / 双通道客户端）同构，建议**直接复用其骨架**，差异仅在：

1. 模板配置从「代码内置 + AI 固化」升级为**独立 YAML 文件 + 启动加载**（本设计 §3）；
2. 列映射键从单列名升级为 `区块.列名`（支持双行表头家族）；
3. 下行接口从「下单双通道」换成「业务订单新增接口」。

## 8. 待确认（阻塞 §6 归集策略与字段映射表）

1. **TMS 业务订单新增接口的字段文档**——必填/选填、字段名、箱信息是嵌套数组还是一单多箱拆分调用。拿到后才能产出「标准模型 → 接口字段」的最终映射表。
2. **四类归集的其余三类**（费用信息？箱信息？应收应付？）——本轮先按业务信息做，但标准模型预留扩展位。
3. 志驿/profitStatement/亚灏的**利润明细表家族是否都属于第一类业务范围**——其应付/车辆成本/公司成本区块大概率属于后续三类，本轮可只映射业务字段 + 应收区块。
4. 应付账单 xlsx（集行格式）是**应付**性质，建议归入后续类别，本轮 8 个家族中先覆盖 7 个应收类家族。

## 9. 接入新模板的流程（运营视角）

```
上传新竞品的账单
  → L1 指纹未命中 → L2 相似度 < 阈值 → 判定为新家族
  → L3：别名字典命中部分列 + LLM 映射剩余列
  → 四道校验（行数范围/必填字段齐全/类型合法/抽样回读）
  → 人工在预览界面确认映射结果
  → 一键固化为 templates/{family}_v{N}.yaml
  → 下次同模板直接 L1 命中
```

代码改动量：**0**。这就是「少用硬代码」的落地方式。
