## 2. R4 取证：单级 error 现状（2026-09-09 源码复核）

### 2.1 构造点（bill 域 4 处，同一 shape）

`create_result.error` 均为手写 dict 三元组 + details：

| 构造点 | code | message | description | details |
|---|---|---|---|---|
| validation.py:51 `reject_unknown_box_types` | `unknown_box_type` | 中文（按单/按文件两态） | 固定兜底"箱型不在 TMS 支持清单中" | `{unknown_box_types: []}` |
| validation.py:95 `reject_missing_bl_no` | `missing_bl_no` | MISSING_BL_NO_MSG | **= message 全文复制** | `{missing_bl_no_count: n}` |
| client.py:220 `_error_result` | `order_upstream_error` | 上游错误原文（可含英文技术态） | `_ERROR_DESCRIPTION` 固定兜底 | `{status_code, upstream_response}` 等 |
| client.py:445 `_missing_bl_result` | `missing_bl_no` | "提单号缺失，未录入" | 另写一段说明 | `{}` |

### 2.2 消费点

| 消费点 | 读的键 |
|---|---|
| service.py:345 `_build_failed_details` | `error.code` / `error.message` → 改名输出 `error_code` / `error_message` |
| import_response.py:92 `bill_import_outcome`（preview/204 文案） | `error.code`（`_MSG_CODES` 优先级）/ `error.message` |
| import_response.py:68（409 分支） | 独立构造审计 `audit_detail` 四元组 `{code, message, description, details}` |
| **error.description** | **bill/manifest 域内零消费**（grep 无读取点；app 侧仅 error_handlers 的 SkillAPIError.description，另一体系） |

### 2.3 双轨表现

1. **error 内部双语义**：`message` 与 `description` 并存——missing_bl_no 场景两者逐字相同（validation.py:101-102、client.py:453-454）；unknown_box_type / order_upstream_error 场景 message 是"真文案"、description 是"固定兜底"，历史残留（早前 message 英文技术态 / description 中文展示态的分工已废弃，见接口文档 §5「msg 原 description，英文 message 不再对外」）。
2. **同一错误两套字段名**：error 内 `code/message` vs 对外摘要 `failed_details` 内 `error_code/error_message`。
3. **接口文档自相矛盾**：§3.1 data 表 `create_result` 定义为 `(success/sn/skipped/error)`；§3.2 定义为 `{success, sn, error}`（漏 skipped）；§3.3 示例与 §3.2 定义一致。

### 2.4 R4 方案（决策点见 §5）

- **error 收敛为 `{code, message, details}`**：删除 description 字段（本地零消费、内容冗余）。message 为唯一用户可读文案；details 承载结构化补充（上游回显、文件级清单等）。
- **failed_details 键名收敛**：`{order_num, error_code, error_message}` → 与 error 同键名 `{order_num, code, message}`（或嵌套整段 error，见 Q2）。
- 409 审计 `audit_detail`：审计落盘结构独立于响应，建议**不动**（保留四元组与全局 error_detail 同构），见 Q3。

## 3. R5 取证：create_result 自由 dict 现状

### 3.1 定义

- schema.py:158（BillOrder）、schema.py:352（CanonicalOrder）：`dict[str, Any] | None`，无模型约束。
- manifest/schema.py:106 同构（若 Q5 联动）。

### 3.2 构造点键全集（bill 域，实测 4 形态）

| 形态 | 场景 | 键 |
|---|---|---|
| 失败（本地拦截/上游拒/HTTP 错） | validation.py ×2、client.py `_error_result`/`_missing_bl_result` | `success:false, [skipped:false], sn:null, error:{...}` |
| 跳过（去重命中） | service.py:325、client.py:326 `_skipped_result` | `success:true, skipped:true, sn, error:null` |
| 成功（AddWork 通道） | client.py:291 | `success:true, sn, error:null, [upstream:data[0]]` |
| 成功（canonical 通道） | client.py:376 | `success:true, sn, o_id, error:null, [upstream:data[0]]` |

不一致点：`skipped` 键部分形态缺失（成功单无）；`o_id` 仅 canonical 成功；`upstream` 仅下游回显存在时；`error` 恒出现（值为 null 或对象）。

### 3.3 消费点 / 断言面

- app 消费点 ~15 处：service.py（summary/upstream 组装）、import_response.py、validation.py（已标记跳过判断）、client.py（提交编排）、fee_bootstrap.py:174/343、master_data/orchestrator.py:68（pending 过滤）——全部 `create_result.get("…")` 自由读键。
- tests：bill 域 6 文件 102 处引用（test_service / import_response / payload / dedup_integration / box_whitelist / route / client / order_full_payload），多为整 dict 构造与相等断言，模型化后 `dict == BaseModel` 不成立，需逐文件同步。

### 3.4 R5 方案（决策点见 §5）

- schema.py 新增 `OrderError`（code/message/details）与 `CreateResult`（success/skipped/sn/o_id/error/upstream）pydantic 模型；BillOrder/CanonicalOrder.create_result 字段类型收口为 `CreateResult | None`。
- 构造点：4 处工厂收敛为模型构造（validation/client/service 内字面 dict 删除，统一形状不再漂移）。
- 消费点：`.get()` → 属性访问（顺带消灭拼写/缺键隐患）。
- 序列化策略见 Q4（补全缺省键 vs 保持旧省略形态）。
