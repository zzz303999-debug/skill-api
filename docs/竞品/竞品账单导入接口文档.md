## 1. 概述

### 1.1 背景

金科信等竞品系统导出的历史应收对账单（`.xls` / `.xlsx`，如「2018-01到2018-12上海秋怡应收对账单.xls」）需要导入本 TMS 系统。本服务负责：解析账单 → 按提单号归集（一票多柜合并）→ 映射为业务订单新增接口（`AddWork`）的字段 → 按开关决定**只返回预览**或**直接逐单创建**。

### 1.2 接口形态（v0.2 变更）

**单接口 + 开关**：`POST /orders/bill/import`，上传文件时通过开关 `create_order` 控制：

| create_order | 行为 |
|---|---|
| `false`（默认） | 只解析并返回预览（含 order_data、缺失字段、未提取到提示），**不下单** |
| `true` | 解析后**直接逐单创建**订单，响应同时返回解析结果与每单创建结果 |

### 1.3 接口定位与四类归集

竞品账单解析归集后，四类数据线分别落入 TMS 对应模块（验收/排查数据是否导入时按此导航）：

| 数据线 | 内容 | 下游动作 | TMS 归属模块（验收路径） |
|---|---|---|---|
| 1. 业务信息 | 业务订单字段（提单号/客户/箱型箱量/门点/司机/车牌等） | `AddWork` 下单 | 业务中心 → 业务订单 |
| 2. 财务信息 | 应收 `shou[]` / 应付 `pay[]` / 成本 `cost[]` 费用条目（含通道合计回写） | 随 AddWork 订单费用传入 | 财务中心 → 应收 / 应付 / 成本 / 车辆成本 |
| 3. 基础信息 | 客户 / 门点 / 司机 / 车辆 | 达阈值建档（计数见 `meta.master_data`） | 车队中心 → 客户 / 门点 / 司机 / 车辆 |
| 4. 费用栏目 | 缺失费目码（price_id=null）自举建档 | `AddCarPrice` 建档（prod 默认关闭） | 常用设置 → 费用管理 |

> 费用为三通道发射（2026-08-19 live 实证：cost 条目 TMS 回显挂 `supplier[]`）；「成本」与「车辆成本」模块的具体归属在 UI 验收时区分确认。通道/归一/自举规则详见《竞品账单导入PRD》§5.10 与《TMS业务订单新增接口-逆推规范》。

### 1.4 核心原则

1. **默认不自动下单**：`create_order` 缺省为 `false`；调用方显式传 `true` 才直接创建，防止误下单
2. **一票一单**：同提单号的多个柜子合并为一个业务订单
3. **零静默错误**：提单号、客户、箱型箱量等关键字段缺失时**不阻塞接口返回**，但必须返回未提取到信息（`missing_fields` / `missing_reasons`），由调用方判断处理；关键数字宁缺勿错
4. **不自动重试**：订单创建请求不自动重试，防止重复下单；失败单由调用方处理后重新提交

## 2. 业务流程

### 2.1 上游侧流程（调用方视角）

```
① POST /orders/bill/import（multipart）
   file: 账单文件
   create_order: false（缺省，只预览） | true（直接创建）
      │
      ├─ create_order=false → 返回 orders[] 预览（order_data / missing_fields / missing_reasons）
      │
      └─ create_order=true  → 服务端逐单创建订单，返回 orders[].create_result + summary
```

- 预览模式下，调用方拿到 `orders[].order_data` 后可人工核对；**修正缺失字段需修改文件后重新导入**（单接口模式无独立提交通道，如需 JSON 直传可后续扩展）
- 创建模式下某单失败**不影响其他订单**，失败原因在 `orders[].create_result.error` 中完整透传
- 下游鉴权（v1.4）：调用方登录 TMS 获取 token，create 模式请求头携带 `sk: <token>`（必填）；服务端原样透传 AddWork/建档（见 2.2），不额外换取凭据

### 2.2 下游侧链路（调用方 → 服务端 → TMS 订单系统）

创建订单时，**调用方先登录 TMS 获取 token**，随后随请求头透传，服务端逐单下单（v1.4 起，不再服务端换取）：

```
① 调用方登录 TMS（页面/系统登录）→ 获得 token（sk 值）
② POST /orders/bill/import（multipart）
   header: sk: <步骤①的 token>（create 模式必填）
   create_order: true
      │
③ 服务端逐单 POST https://s3.jxt56.com/Car/WorkOut/AddWork
   header: sk: <透传同一 token>
           content-type: application/x-www-form-urlencoded; charset=UTF-8
   body:  a={}&b=<URL编码JSON>&c={}&<顶层展平表单字段>（见 5.3）
```

> 技术确认：**不走页面登录、不服务端换取**（2026-08-19 定论，原 GetWebKey → login 链路及
> `JXT_EXT_APP_ID` 等凭据配置已移除）；同一批订单共用该 sk；sk 无效/过期由 AddWork 端判定
> → 该单失败 error 透传（不抛整请求错误）。
> **preview 模式**（create_order=false）零下游调用，不要求 sk。

**AddWork 请求体形态（已通过实际抓包确认，2026-08-11）**：

表单共四组参数：
- `a` = `{}`（固定空对象）
- `b` = URL 编码的 JSON 字符串（键含 `data[0][b_order_num]` 等展平写法，与顶层字段重复）
- `c` = `{}`（固定空对象）
- 顶层展平字段：**242 个键值对**，业务字段以 `key=value` 直接展平，数组用 `key[N][subkey]`，费用条目用 `shou[N][费用名称][属性]`（中文费用名作键）

**关键业务键名（已确认）**：
- 订单：`order_num1`（提单号）、`type`（固定 1）、`c_title`、`c_name`、`c_phone`、`c_sn`、`c_note`、`c_id`、`month`（YYYY-MM）
- 运输：`b_ship_name`、`b_ship_num`、`b_ship_company`、`b_start_dock`、`b_end_port`、`b_end_dock`、`b_wharf`、`b_open_ship_time`、`b_close_ship_time`、`b_operator`
- 门点：`factory_name`、`factory_bei`、`factory_id`、`b_factory_not`、`b_tare`
- 明细：`data[N][b_order_num/j/m/t/hh/mt]`、`box[N][b_type/box_num]`
- 司机/做箱：`driver[N][d_id/b_date/b_date_time_start/b_get_address/b_back_address/d_name/d_num/d_phone/distance/you_hao/driver_note/get_ys_zj/pay_yf_zj]`
- 费用（**本期发送应收 `shou[]`；应付/双拖/成本不发送**）：`shou[N]`（应收）条目键为**费用中文名**（运费/待时费/预提费/洋山费/落还箱费/其它费），属性暂仅传 `money`（其余 `price_id/price_type/is_profit/dai_dian/cost_id/lock_status/customer_tax_rate/class_id` 待实测）；`pay[N]`（应付）、`duo_get[N]`（双拖应收）、`cost[N]`（成本）**本期不发送**；合计：`driver[0][get_ys_zj]`（应收合计=各 shou 金额之和）、`driver[0][pay_yf_zj]`（应付合计，本期 0.00）、`duo_get[0][duo_get_hj_zj]`、`cost[0][supplier_hj_zj]`
- 系统：`user_name`、`car_name`、`section_name`、`appendCost=true`、`o_id`（新建为空）、`img_data=[]`、`img_data_id=[]`

> **注意**：请求体中**没有箱号字段**（`box[]` 仅 `b_type/box_num`）；箱号需汇总写入 `c_note` 兜底（见 5.1）。
```

> **AddWork 响应（已通过实际抓包确认，2026-08-11）**：
> 成功：`{"code": "200", "msg": "添加成功", "data": [{..., "sn": "EX26080042", "sns": "EX26080042-1", "o_id": 20997568, "od": "1786429395", "order_num1": "222", "b_type": "20GP", "b_jmt": [...], "work_type": "出口"}]}`
> - `data[0].sn`：订单编号；`data[0].sns`：子订单编号（含箱号后缀）——创建成功标识，写入 `create_result.sn`
> - `data[0]` 为完整订单对象（含 o_id/od/order_num1/b_type/b_jmt/price/driver 等），可作溯源
> - 失败：`{"code": "204", "msg": "添加失败"}`（沿用 publishCreateOrder 文档口径，待抓包复核）

### 2.3 一票多柜归集规则

- 按**提单号**分组：同一提单号的所有行合并为一个订单
- `box[]`：同箱型数量累加（如 2 行各 40HQ → `[{"b_type": "40HQ", "box_num": 2}]`）；箱型**不做格式校验，非空即合法**（2026-08-12 业务确认：标准箱型及 大冷/飞翼车/2X20/拼箱 等非标表述均正常归集），仅列为空才标记缺失
- `data[]`：每柜一行，仅含该行提单号 `b_order_num`（AddWork 无箱号字段，箱号汇总入 `c_note`，见 5.1）
- `driver[]`：合并后只有一条，各字段取组内第一条（按序号排序）非空值；`b_date` 同前；各柜日期不一致时，其余日期并入 `c_note`
- 组内行按账单「序号」排序，保证 `data[]` 顺序与账单一致
- 提单号为空的行：单独成组并返回未提取到提示（避免与其他票合并）
- 费用：同费用名（如运费）多行金额**累加**为一条 `shou` 条目（一票多柜合并）；非数字值（含中文大写金额）跳过该条目

### 2.4 日期补年份规则

- 账单内日期通常只有月-日（如 `1-27`），年份从账单抬头「结算日期：2018-01-01-2018-12-31」区间推断：
  - 优先取落在结算区间内的年份（跨年账单如 `2018-01~2019-12` 时 `12-7` 补为 `2018-12-07`、`1-5` 补为 `2019-01-05`）
  - 无法推断（如日期非法、无结算区间）→ `b_date` 置 null、`month` 置空（`b_date` 为**非必填**，缺失不返回未提取到提示）

## 3. 接口定义

### 3.1 基本信息

| 项目 | 值 |
|---|---|
| 路径 | `POST /orders/bill/import` |
| 内容类型 | `multipart/form-data` |
| 鉴权 | 需要（Bearer Token 或 X-API-Key） |
| 下游 token | create 模式必填：请求头 `sk: <TMS token>`（调用方登录 TMS 获取，v1.4 起；preview 不要求） |
| 限流档位 | heavy（默认 60 秒内 10 次） |
| 是否调用下游 | 仅 `create_order=true` 时调用 |

### 3.2 请求参数

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `file` | file | ✅ | 竞品应收对账单文件。支持 `.xls` / `.xlsx` / `.xlsm`；大小上限 20 MB |
| `create_order` | bool | ❌ | 是否直接创建订单。缺省 `false`（只预览不下单）；传 `true` 时逐单调用下游创建接口 |
| 请求头 `sk` | string | create 时 ✅ | 调用方登录 TMS 获取的 token（v1.4 起）；服务端透传 AddWork 下单与建档；缺失 → 400 `bad_request` |

### 3.3 响应总览

响应统一包含解析结果；仅 `create_order=true` 时附带逐单创建结果：

| 字段 | 类型 | preview | create | 说明 |
|---|---|---|---|---|
| `file` | string | ✅ | ✅ | 上传文件名 |
| `bill_period` | string \| null | ✅ | ✅ | 结算区间 `YYYY-MM-DD~YYYY-MM-DD` |
| `total_rows` | int | ✅ | ✅ | 识别到的数据行数（一柜一行） |
| `order_count` | int | ✅ | ✅ | 归集后的订单数（按提单号合并） |
| `create_order` | bool | ✅ | ✅ | 回显本次开关取值 |
| `orders[]` | array | ✅ | ✅ | 订单列表（既有语义管线），字段见 3.4 |
| `orders[].create_result` | object \| null | null | ✅ | 该单创建结果（success/sn/skipped/error） |
| `canonical_orders[]` | array | ✅ | ✅ | TMS 通道标准订单列表（标准字段管线；既有语义管线为空），字段见《标准业务订单模型-字段映射表》§1，含 `create_result`（同 orders[].create_result） |
| `summary` | object \| null | null | ✅ | 汇总：total / success / failed / **skipped** / **created** / success_sns / failed_details（含 error_upstream 上游业务码，与单级 error.details.upstream 同构） |
| `upstream` | object \| null | null | ✅ | 上游业务码回显（§3.7）：新建成功 `{"code":"200",...}`；全部失败 `{"code":"204",...}`；preview/无新建/全部 skipped 为 null |
| `meta` | object | ✅ | ✅ | 溯源信息（文件哈希、解析时间、引擎、模板、未映射表头等） |

### 3.4 orders[] 元素字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `order_num1` | string \| null | 提单号（订单号）；缺失/非法时为 null |
| `c_title` | string \| null | 客户名称；缺失时为 null |
| `container_count` | int | 该订单柜数 |
| `row_count` | int | 该订单原始账单行数 |
| `missing_fields` | string[] | 未提取到字段名，见 5.2 |
| `missing_reasons` | object | 未提取到字段 → 中文原因 |
| `order_data` | object | 下单接口的请求体数据（嵌套结构；**必填项未提取到时对应字段为 null，不用空字符串或 0 填充**；发送 AddWork 时 null 展平为空字符串；人工修正需改文件后重新导入） |
| `create_result` | object \| null | 创建结果：`{success: bool, sn: string\|null, error: object\|null}`；preview 模式为 null |

### 3.7 create 模式行为约定

- **sk 由调用方透传，逐单创建**：调用方登录 TMS 获取 token 后经请求头 `sk` 透传（一次），服务端串行调用 AddWork 逐单创建；某单失败不影响后续订单；sk 无效由 AddWork 端判定 → 该单 error
- **不自动重试**：下游超时/拒绝时不重试（防重复下单）；调用方根据 `orders[].create_result.error` 决定是否重提
- 存在未提取到字段（`missing_fields` 非空）的订单**照常提交**（开关语义是"是否创建"，不是"是否放行"）；**本服务不拦截**，未提取到信息随响应返回，是否放行由调用方判断（可先 preview 核对后决定是否 create）
- create 模式缺 `sk` 头（调用方未登录 TMS）：返回 400 `bad_request`（details.upstream 携带 `{"code": "400", "msg": "缺少 TMS token（sk 请求头），请先登录 TMS", "data": []}`），不进入解析/下单流程
- **`upstream` 回显（对齐 TMS 通道格式）**：create 模式且本批确有新建成功单时固定返回 `{code, msg, data}`——新建成功 → `{"code": "200", "msg": "添加成功", "data": [每单原始回显（含 `sn`/`sns`）]}`（下游成功但无回显时 `data` 为空，业务码仍为 200）；新建全部失败 → `{"code": "204", "msg": "添加失败", "data": []}`（失败明细见 `summary.failed_details`）；preview 模式、无单可创建或全部 skipped（重复上传）时为 `null`
- **重复上传（409）**：create 模式全部命中注册表（无新建）时返回 HTTP 409，`error.details.upstream` 同样携带 `{code, msg, data}` 结构——`{"code": "409", "msg": "账单已全部创建过", "data": [{"sn": "<已创建单号>"}]}`，调用方可与 200 场景统一按 `upstream.code` 判断业务结果
- **数据超限（400）**：数据行数超过上限时返回 HTTP 400 `too_many_rows`，`error.details.upstream` 携带 `{"code": "400", "msg": "数据量过大，联系人工客服", "data": []}`——全场景（200/204/400/409）业务码均在 `upstream.code` 统一可达
- **兼容性提示**：`upstream.code` 为字符串（对齐 TMS 通道格式），如 `"200"`/`"204"`；旧版本曾为数值 200，对接方若按数值严格相等判断需同步兼容 str/int
- **批量耗时提醒**：订单逐单串行创建，大账单（数千单）单请求可能耗时数分钟；建议调用方分批导入（单次建议 ≤ 2000 单，超出建议拆分文件），并适当放宽客户端超时（服务端反向代理超时已放宽至 1 小时，实测 1850 单 ≈ 54 分钟）

### 3.8 重复上传去重（v1.2 新增）

**同一提单号全局只允许创建成功一次**（成功单注册表 `storage/imported_orders.json`）：

- create 模式下逐单创建前先查注册表，命中（该提单号已创建成功）→ 该单**跳过**：`create_result = {success: true, skipped: true, sn: <首次创建的 sn>, error: null}`，不调用下游
- **只登记创建成功单**：失败单/未提交单不登记，修正文件后重导失败单照常创建（不被误拦）
- 键规范化：提单号 strip 首尾空白 + 统一大写（假设 TMS 不区分大小写）
- 并发：同一提单号跨请求串行化（per-bl_no 锁包住查重→提交→登记），并发上传同一文件不会重复下单
- summary 新增计数：`skipped`（本次跳过数）、`created`（本次实际新建数 = success − skipped；success 含 skipped 单）
- **清除方法**：删除 `storage/imported_orders.json` 即全量重置（TMS 手工删单后想重导需先执行）；preview 模式零副作用（不读写注册表）
- **已知限制**：
  1. 依赖单进程部署（进程内锁 + 单文件存储），多 worker/多实例需换共享存储
  2. 下游「已创建但响应超时」假失败（本地未登记）→ 重导可能重复，需 TMS 查询接口（方案二）兜底
  3. 并发冲突残留窗口：预判未命中但提交时被另一请求创建 → 本请求 skip，该单仍计入本次建档计数（仅并发冲突时发生）

## 4. 错误码约定

所有错误统一为：

```json
{
  "error": {
    "code": "错误码（英文 snake_case，机器可读）",
    "message": "技术性英文说明（定位用）",
    "description": "中文说明（可直接展示给用户）",
    "details": { }
  }
}
```

### 4.1 本功能相关错误码

| HTTP | 错误码 | 触发场景 | 中文说明 |
|---|---|---|---|
| 400 | `bad_request` | 文件扩展名不支持、内容无法解析为账单（找不到含「客户编号」「提单号」的表头行）、空文件；**create 模式缺 `sk` 请求头（v1.4）** | 请求参数或上传内容不合法，请检查后重试 |
| 400 | `file_format_mismatch` | 文件扩展名与实际内容格式不符（如 .xls 实为 xlsx） | 文件扩展名与实际内容格式不符，请检查文件是否正确 |
| 400 | `file_too_large` | 上传超过 20 MB | 上传文件超过大小限制，请压缩或拆分后重试 |
| 400 | `too_many_rows` | 单次导入数据行数超过上限（默认 10000 行，一柜一行） | 数据量过大，联系人工客服 |
| 400 | `empty_file` | 上传文件为空 | 上传文件为空，请重新上传有效文件 |
| 413 | `payload_too_large` | 请求体超限 | 请求体超过大小限制，请压缩或拆分后重试 |
| 422 | `convert_error` | `.xls` / `.xlsx` 文件损坏或加密无法打开 | 文档转换失败：文件可能已损坏或格式不受支持，请转换格式后重试 |
| 502 | `order_upstream_error` | 下游系统级拒绝（AddWork/建档不可达或拒单） | 订单系统拒绝了请求或不可达，请稍后重试 |
| 429 | `rate_limited` | 触发 heavy 限流 | 请求过于频繁，已被限流，请稍后重试 |
| 401 | `unauthorized` | 凭证缺失/错误 | 未授权访问，请提供有效的访问凭证（API Key） |
| 503 | `server_busy` | 并发处理任务满，排队超时（10 秒） | 服务繁忙（并发处理任务已满），请稍后重试 |
| 500 | `internal_error` | 服务内部错误 | 服务内部错误，请稍后重试或联系管理员 |

> 注意：
> - 账单内某行/某订单字段缺失**不报错**（返回 200 + `missing_fields` / `missing_reasons` 未提取到信息），只有文件级/请求级问题才返回非 200
> - 单笔订单创建失败**不触发**整请求错误（见 3.6 的 `orders[].create_result.error`）

### 5.2 未提取到字段与提示

必填项未提取到时，在 `missing_fields` / `missing_reasons` 返回未提取到信息（满足其一）：

| missing_fields 取值 | 触发条件 | missing_reasons 可能值 |
|---|---|---|
| `order_num1` | 提单号为空，或清洗后不足 8 位/含非法字符/纯字母 | `原文未找到` / `格式不合法` |
| `c_title` | 客户名称为空 | `原文未找到` |
| `box` | 箱型缺失/非法被跳过，导致该单无有效箱型箱量（`box[]` 为空） | `原文未找到` / `格式不合法` |

- **必填项未提取到**（`order_num1` / `c_title` / `box[]` 任一缺失）：`order_data` 中对应字段置 `null`（**不用空字符串或 0 填充**），并在 `missing_fields` / `missing_reasons` 返回未提取到信息（含中文原因）；补充需修改文件后重新导入
- 必填字段以《订单创建接口文档》v1.0 为准：`order_num1`、`type`（固定 1）、`c_title`、`data[].b_order_num`（随 `order_num1` 联动）、`box[]`；`driver[].b_date` 为**非必填**，缺失不返回未提取到提示
- `missing_fields` 为空表示业务信息必填字段齐备，可安全提交
- **本服务不拦截、不判断**：未提取到信息仅随响应返回给调用方，由调用方决定照常创建 / 修正后重新导入 / 放弃；create 模式下缺失单照常提交，由 AddWork 端校验决定成败

## 6. 注意事项

1. **默认不下单**：`create_order` 缺省 `false`；生产调用务必显式传值，避免歧义
2. **限流**：接口属 heavy 档（与 `/orders` 同档），默认 60 秒内每 IP 10 次；生产环境建议开启限流；内网 IP 可配白名单豁免
3. **文件大小**：单文件 ≤ 20 MB；`.xls` 老格式与 `.xlsx` 均可（`.xls` 通过 xlrd 解析）
4. **数据行数**：单次导入 ≤ 10000 行（一柜一行，按解析原始数据行数校验，含尾部合计/锚点行；归集后的 `total_rows` 可能小于原始行数）；超限返回 400 `too_many_rows`，请拆分后分批导入
5. **文件粒度**：一次上传一个账单文件（一个结算周期）；跨年/多公司账单请分文件导入
6. **一票多柜**：合并规则见 2.3；若业务上需要每柜一单，请在预览结果中按 `data[]` 拆单后再以 `create_order=true` 重新导入
7. **幂等**：create 模式不自动重试；重试前请确认失败单未在下游创建成功（下游可能已创建但响应超时）
8. **鉴权（本服务）**：接口需有效凭证；生产环境必须配置 API Key
9. **鉴权（下游，v1.4）**：调用方登录 TMS 获取 token 后，create 模式请求头携带 `sk`（必填，缺失 → 400）；服务端原样透传 AddWork/建档（同一批共用）；sk 无效由下游判定，不抛整请求错误；服务端不再持有任何 TMS 凭据
10. **审计**：请求/响应自动写入访问日志（含文件哈希、订单数、逐单结果），可在 `/logs` 页面查询
11. **去重（v1.2）**：create 模式按提单号全局去重（见 §3.8）；注册表文件 `storage/imported_orders.json` 只增不减，需定期评估容量/清理；依赖单进程部署
12. **兼容性**：表头按列名匹配（而非固定列号），账单列顺序变化不影响解析；表头需同时含「客户编号」「提单号」两列才能识别（真实账单无「业务编号」列，客户编号实为委托号）
13. **箱号处理**：AddWork 请求体无箱号字段（`box[]` 仅 `b_type/box_num`），全部箱号汇总入 `c_note` 备注（如「箱号：XXX,YYY」）兜底，不丢数据；注意备注超长风险（见 7 清单 #7）
14. **并发**：解析在服务端线程池执行（上限 4 并发），满负荷排队超 10 秒返回 503
